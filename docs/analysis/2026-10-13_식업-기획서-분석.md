## 1. 한 장 요약

- **무엇**: 외식업 사장님용 소모품 B2B 오픈마켓 + 본사 디자인팀이 중계하는 맞춤 인쇄(수저집·컵 로고). 고객과 파트너는 직접 만나지 않고, 디자인 협의는 디자인팀↔고객, 생산 협의는 디자인팀↔파트너로 분리됩니다.
- **채널 3개, 실행 앱 3개**: 고객 웹앱(웹뷰 앱 포함)·파트너 센터 = `web`, 통합 관리자·디자인 스튜디오 = `admin`, 정산·알림 = `batch`, 파일 미리보기 = 격리된 `convert`. 코드·DB는 하나(모듈러 모놀리스).
- **기능 규모**: 명세서 161개 기능 = 정식 오픈(MVP) 118 · 오픈 후 3개월(2차) 34 · 1년 안(3차) 9. (10-13에 P-PRD-09·U-PDP-07이 MVP로 추가돼 159·116에서 늘었습니다.)
- **돈의 흐름**: 고객 결제 1건 안에 파트너 몫(상품·판비)과 본사 몫(디자인비·옵션·멤버십·PB)이 섞임 → PG에서 판매자별로 나눠 기록 → 구매 확정이 정산 이벤트가 되어 주 1회 지급(구매 확정 후 최대 10일).
- **수익의 핵심 지표**: 같은 디자인 재주문. 맞춤형 첫 주문은 거의 남지 않고(유료 약 3천 원, 50만원 무료 기준 이상이면 적자), 재주문은 수수료 3%p를 내려도 주문당 약 1만 5천 원이 남습니다(11장). 그래서 재주문을 직거래로 뺏기지 않는 장치(수수료 인하·연결 보장·계약 조항)가 설계 전반에 퍼져 있습니다.

## 3. 핵심 프로세스 4개

1. **일반 주문**: 장바구니(파트너+출고지+출고 유형 묶음) → 6단계 금액 계산(구간 단가 → 파트너 할인 → 디자인비 판정 → 본사 쿠폰 → 배송비 → 포인트) → PG 결제(서버 재계산·결과 재확인) → 파트너별 하위 주문 → 발주 확인 → 송장 → 배송 완료(택배 API) → 7일 뒤 자동 구매 확정 → 정산 이벤트.
2. **맞춤 주문**: 디자인 방식 4종 선택 → 요청서 → 선결제 → 배정(영업시간 4시간) → 첫 시안(영업일 2일) → 핀 코멘트·수정(무료 3회) → 체크리스트 5개 확정(사양 스냅샷·해시·동의) → 인쇄 패키지 전달 → 파트너 [인쇄 가능] = 생산 시작(이후 취소 불가) → 출고. 곁가지: 무응답 3/14/30일, 확정 후 변경·취소(생산 보류 플래그 + 본사 중재), 인쇄 반려.
3. **재주문**: 이전 확정 스냅샷 복사 → 디자인 단계 없이 `APPROVED → HANDED_OFF` → 판비 면제 → 파트너 수수료 맞춤 13% − 3%p. 생산 전이면 공제 없이 바로 취소.
4. **주간 정산**: 정산 이벤트(구매 확정·클레임 완료·중재·조정) → 화요일 마감 → 보류 분리 → 수~목 확정 → 금요일 PG 지급대행(요청자 ≠ 승인자). 지급액 = Σ이벤트 − 본사 청구(분쟁 조정 → 위약금 → 플랜료 → 광고비, 한도 = 그 주 정산액) + 이월.

## 4. 잘 짜인 부분 (그대로 가져가면 되는 것)

- **돈 계산이 한 곳에 모여 있고 예시 숫자가 있다.** C-PRICE-01·C-PAY-02·C-STL-01의 예시를 프로토타입 엔진(`prototype/assets/engine.js`)으로 그대로 재현했고, 18개 검사가 모두 통과합니다(결제 134,000원 / MVP 144,000원, 부분 취소 환불 45,000원 = 660P + 44,340원, 지급액 274,550원, 3주 이월·미수금 42,000원, 연간 멤버십 환불표 등). 숫자끼리 서로 어긋난 곳은 찾지 못했습니다. 11장 "주문 1건당 남는 돈" 표와 멤버십 손익(약 −1,300원, 본전 구매 증가율 41%)도 검산이 맞습니다.
- **상태를 주문 항목 단위로 두고 전이표로만 움직인다**(C-STATE-01·02). 낙관적 잠금(상태 버전)과 동시 이벤트 처리 규칙까지 있어 구현 기준이 분명합니다.
- **결제 시점 스냅샷**으로 부분 취소·반품을 재계산하는 원칙, **"결제 요청 시점 = 가격 보장"**, **정책값 분리**(A-SYS-03)가 일관됩니다.
- **분쟁 대비 장치**: 공식 결정은 버튼으로만, 확정 스냅샷·해시·동의 시각·IP, 연락처 자동 가림, 다운로드 기록.
- **보안 설계**: admin 앱 분리·VPN, 파일 변환 격리(convert), 파트너 `partner_id` 범위 조회, 개인정보 blind index.

## 5. 개발 관점에서 가장 무거운 곳 (위험 순)

1. **PG 정산 구조 미확정(15장 Q6)** — 하위몰형인지 토스식 지급대행형(플랫폼=가맹점, 잔액 송금)인지에 따라 C-PAY-01(판매자별 기록), C-PAY-02(판매자 지정 부분 취소), A-STL-02(지급), 증빙 명의(U-ORD-05)가 달라집니다. 주문·결제·정산 세 도메인의 핵심 코드가 이 결정 뒤에 있습니다. → **주문·결제 개발 착수 전에 가장 먼저 닫을 결정.**
2. **금액 재계산(C-PRICE-01 · C-PAY-02)** — 안분 끝전, 쿠폰 조건 재판정, 무료배송 재계산, 디자인비 고정, 포인트 10P 내림, 0원 이하 처리까지 엮여 있습니다. 프로토타입 엔진이 명세서 예시를 모두 통과하므로, 실제 개발 때 **이 검사 18개를 JUnit으로 먼저 옮기고** 구현하는 순서를 권합니다(기획서 09장 "돈 계산은 테스트로 지킨다"와 같은 방향).
3. **디자인 상태 머신과 주문 항목 상태의 짝 맞추기** — 디자인 요청 16개 상태(자체 파일 3개 포함), 확정 후 변경으로 `APPROVED/HANDED_OFF → REVISION`과 주문 항목 `DESIGN_CONFIRMED → DESIGNING`이 함께 되돌아가야 하고, 고객 요청과 파트너 [인쇄 가능]이 동시에 오면 상태 버전으로 하나만 반영해야 합니다(D-APV-02). 이 부분은 상태 전이 테스트를 따로 두는 게 안전합니다.
4. **두 앱에 걸친 실시간 협의 룸** — 고객은 web, 디자이너는 admin에 붙고 Redis pub/sub로 중계, 재연결 시 누락 메시지 동기화, 10분 알림톡 묶음. 1인 개발 기준 3~4주로 잡혀 있는데, 마스킹·파일 미리보기·핀과 엮이면 가장 일정 변동이 큰 덩어리입니다(기획서에 Sendbird 대안 명시).
5. **웹뷰 쉘의 결제·본인인증 앱 호출(C-APP-03)** — 카드사·간편결제별 앱 스킴, SameSite 쿠키로 세션이 빠져도 주문 토큰으로 결과 확인. 실기기 테스트 목록이 필요합니다.

**법률 자문 전 초안으로 화면에 들어간 문구** (자문 답이 오면 확정해야 함): 판(동판) 소유권·사용 조건, 직거래 금지·고객 비유인(종료 후 12개월, 위약금 수수료율 × 3배·최소 50만원), 회사 디자인 무단 인쇄 = 저작권 침해, 재주문 인센티브 계약 조건. 그 밖에 1순위 질문(디자인비 공제, 청약철회 제한 동의, 사업자 구매자의 소비자 지위, 통신판매중개자 고지, 연간 멤버십 중도 해지 환불)이 남아 있습니다. 프로토타입 화면에는 해당 문구 옆에 "법률 자문 전 초안" 표시를 붙였습니다.

## 8. 개발 우선순위 제안 (일정 없이 순서만)

기획서 12장의 MVP 개발 순서(기반·회원·상품·검색 → 주문·결제·클레임 → 맞춤 디자인·협의 룸 → 관리자·정산·알림 → 웹뷰 쉘)를 유지하되, 다음 두 가지를 앞으로 당기는 것을 권합니다.

1. **Q6(PG 정산 방식) 확정** — 주문·결제 착수 전.
2. **금액 엔진 + 상태 전이표를 라이브러리로 먼저** — `core`에 가격·환불·정산 계산과 상태 머신(주문 항목·디자인 요청·클레임·정산)을 화면 없이 만들고, 명세서 예시 숫자 테스트로 고정. 프로토타입 엔진이 그대로 참고 구현입니다.
3. 이후 회원 → 카탈로그 → 주문·결제 → 맞춤 디자인(룸 포함) → 정산·관리자 → 웹뷰 쉘.

- 외부 서비스(PG·본인인증·국세청·계좌 인증·전자계약·S3·택배·팝빌)는 화면 안 안내 창으로 대신하고, 알림톡·푸시는 작업 기록의 "알림"으로 남깁니다. 디자인 요청서 규칙(브라우저 기본 경고창 대신 자체 확인 창)에 맞춰 `alert()` 대신 안내 창을 썼습니다.
