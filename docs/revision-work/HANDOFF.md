> 시작: 2026-10-14. 근거: `docs/analysis/2026-10-13_식업-기획서-분석.md` **부록 B**(B1~B63, 209줄부터).
> 사용자는 컨텍스트 관리를 위해 세션을 끊어서 진행한다. **새 세션은 이 파일부터 읽는다.**

## 새 세션 시작할 때 (매번)

1. 이 파일의 "세션 계획"에서 이번 세션 번호와 범위를 확인하고, "항목 체크리스트"에서 그 세션의 ☐ 항목만 골라낸다.
2. `decisions.md`에서 해당 결정(D번호)을 읽는다. **결정이 ☐(미정)인 항목은 손대지 말고 사용자에게 묻는다.**
3. 부록 B는 **필요한 행만** 읽는다: `grep -n '^| B12 |' docs/analysis/2026-10-13_식업-기획서-분석.md`. 분석 문서 전체(약 60KB)를 읽지 않는다.
4. 원본 HTML이 마지막 세션 뒤 사람 손으로 바뀌었는지 본다: 아래 "세션 기록"의 마지막 시각보다 `sikup-*.html` 수정 시각이 새로우면, 사용자에게 무엇을 바꿨는지 묻거나 `docs/prototype-work/texts/`를 다시 뽑아 diff부터 본다.

## 작업 규칙

- **줄 번호는 `docs/revision-work/baseline/*.txt`(2026-10-14 고정본) 기준**이다. 원본 HTML을 고치면 `docs/prototype-work/texts/` 줄 번호는 밀리므로, 부록 B 원문은 baseline에서 `sed -n '1347p'`로 보고 실제 HTML에서는 **기능 ID(`id="D-APV-02"`)나 문구로 찾는다.**
- 원본 HTML(`sikup-spec.html` 720KB, `-plan` 277KB 등)은 **통째로 읽지 않는다.** Grep으로 ID·문구 위치를 찾고 그 근처만 Read → Edit.
- 같은 HTML을 여러 에이전트가 동시에 고치지 않는다(충돌). 조사는 서브에이전트에 맡겨도 되지만 수정은 한 곳에서 순서대로.
- 결정을 반영하면 **결정 기록도 남긴다**: 명세서 `#g-dec` "확정된 결정" 표에 행 추가, 기획서 15장 "확정 사항"에 날짜 소제목(예: "확정 (2026-10-1x 추가 · 부록 B)") 아래 추가. 기존 표기 방식을 그대로 따른다.
- 금액·요율은 전부 관리자 설정값이다. 새 숫자가 생기면 A-SYS-03 정책값 표에 키를 같이 넣는다. 값의 적절성은 따지지 않는다.
- "법률 자문 전 초안" 표시는 자문 답이 오기 전까지 떼지 않는다. 새로 넣는 법적 성격 문구(D11 탈퇴 표 등)에도 같은 표시를 붙인다.
- 일정·자금 조달·경쟁 이야기는 넣지 않는다.
- 문서 문체는 원본(쉬운 말, "~합니다")을 따른다.

## 세션 끝낼 때 (매번)

1. 고친 HTML 검사: `python -I docs/revision-work/tools/check_html.py sikup-spec.html sikup-plan.html ...` → 명세 기능 수(지금 162 = mvp 119 · p2 34 · p3 9 — S4a에 C-STATE-03 추가, 기능을 추가했으면 그만큼 늘어야 함)·중복 ID 없음·태그 여닫이 맞음.
2. 추출본 다시 뽑기: `python -I docs/prototype-work/tools/html2txt.py sikup-spec.html docs/prototype-work/texts/spec.txt` (고친 문서마다. 파일 이름: plan·spec·brief·legal-consult·pg-consult).
3. 옛 문구가 남아 있지 않은지 Grep으로 확인(예: B3이면 "넘으면" 검색).
4. 아래 체크리스트에서 끝낸 항목을 ☑로 바꾸고, "세션 기록"에 한 줄(날짜·시각·한 일·남은 일) 추가.
5. 사용자에게 짧게 보고: 고친 항목 수, 문서별 변경, 다음 세션.
